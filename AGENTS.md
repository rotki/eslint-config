# @rotki/eslint-config

Shared ESLint flat config for rotki TypeScript, JavaScript and Vue projects, published to npm as
`@rotki/eslint-config`. It is based on [antfu/eslint-config](https://github.com/antfu/eslint-config)
and adds rotki's own configs (sonarjs, slop, the `@rotki/eslint-plugin` rules, vue-i18n, storybook,
jsdoc with tsdoc). The main consumer is the rotki frontend (`rotki/rotki`, `frontend/`), which pins
it through its pnpm catalog.

This file is the maintenance guide for humans and coding agents. `CONTRIBUTING.md` covers the
contributor-facing basics (commit style, linting, pull requests).

## Toolchain

- Node.js 24 (`.nvmrc`; CI reads its version from there). `engines.node` is `>=24 <25`.
- pnpm 12, pinned through `packageManager` in `package.json`.
- ESLint 9 and 10 are supported (`peerDependencies`).
- Build: `tsdown` (`tsdown.config.ts`). Tests: Vitest.
- The repository lints itself with its own source through `eslint.config.ts`.

## Layout

- `src/factory.ts`: the `rotki()` factory. It reads the options, detects Vue and TypeScript with
  `local-pkg`, and assembles the config list.
- `src/configs/<name>.ts`: one config module per area (javascript, typescript, vue, stylistic,
  unicorn, markdown, sort, sonarjs, slop, ...), exported through `src/configs/index.ts`.
- `src/options.ts`, `src/types.ts`: option types and their documentation.
- `src/config-presets.ts`: `CONFIG_PRESET_FULL_ON` / `CONFIG_PRESET_FULL_OFF`, used by the tests.
- `src/plugins.ts`: plugins imported eagerly. Optional plugins are loaded lazily inside their
  config with `interopDefault(import(...))` and `ensurePackages`.
- `src/globs.ts`: shared file globs. `src/vendor/`: vendored code and type shims.
- `src/typegen.d.ts`: rule option types generated by `scripts/typegen.ts`. It is git-ignored and
  rebuilt by `pnpm run gen`, which `pnpm run build` runs first.
- `test/factory-snap.test.ts`: snapshots of the resolved config for several option sets
  (`test/__snapshots__/factory/*.snap.json`).
- `test/fixtures.test.ts`: lints `fixtures/input/` with `--fix` under several option sets and
  snapshots the result in `fixtures/output/<option-set>/`.
- `.upstream-sync`: the antfu/eslint-config version last reviewed (see Upstream sync).

## Commands

| Command                   | What it does                                |
| ------------------------- | ------------------------------------------- |
| `pnpm run build`          | Typegen, then build `dist/`                 |
| `pnpm run gen`            | Regenerate `src/typegen.d.ts` only          |
| `pnpm run typecheck`      | `tsc --noEmit`                              |
| `pnpm run lint`           | Lint the repository with its own config     |
| `pnpm exec vitest run`    | Run the tests once                          |
| `pnpm exec vitest run -u` | Run the tests and update snapshots          |
| `pnpm run dev`            | Watch build plus `@eslint/config-inspector` |

CI (`.github/workflows/ci.yml`) runs commitlint, then build, typecheck, tests and lint. Run the same
before opening a pull request.

## Tests and snapshots

- **Build before testing.** The fixture test writes an `eslint.config.js` that imports
  `@rotki/eslint-config`, which resolves to this package's `dist/`. Without a fresh build it lints
  with stale code, and without any build ESLint fails, every output equals its input, and the test
  deletes the expected files under `fixtures/output/` while still passing. Run
  `pnpm run build` before `vitest`, and after every source change.
- **Read snapshot diffs before accepting them.** `vitest run -u` accepts everything. Changes in
  `test/__snapshots__/factory/` show rules added, removed or reconfigured. Changes in
  `fixtures/output/` show how linting results change for real code. Every change there should be
  explained by the commit that causes it, and the commit message should say so when it affects
  consumers.
- When a change touches several concerns that each move snapshots, commit them separately and
  regenerate the snapshots at each step, so every commit carries its own snapshot changes.

## Changing rules and adding configs

- **Changing a rule** in an existing config: edit `src/configs/<name>.ts`, rebuild, update
  snapshots, and check the effect on the rotki frontend (below). Say in the commit body what the
  rule does and how many reports it produced on the frontend.
- **Adding a config** (see `d0b2c02`, the sonarjs config, as an example):
  1. `src/configs/<name>.ts`, exported from `src/configs/index.ts`.
  2. The option in `src/types.ts` / `src/options.ts`, the dispatch in `src/factory.ts`, and the
     presets in `src/config-presets.ts`.
  3. Add the config to `scripts/typegen.ts` so its rule types are generated.
  4. If it needs a plugin that not every consumer uses, add the plugin as an optional peer
     (`peerDependencies` plus `peerDependenciesMeta`) and as a dev dependency, and load it lazily.
  5. Enable it in `eslint.config.ts` if this repository should use it, and document the option in
     `README.md`.
- Keep rotki-specific choices explained in a comment next to the rule. Several rules are
  configured differently from upstream on purpose.

## Checking a change against the rotki frontend

Any change that can alter lint results (rule changes, dependency majors, and in practice also
minor plugin updates) should be measured on the frontend before release. Do not modify the
frontend checkout itself; work on a copy.

1. Pack this branch:

   ```sh
   pnpm pack --pack-destination <scratch>/pack
   ```

2. Copy the frontend's tracked files to a scratch directory and install with its own lockfile:

   ```sh
   cd <rotki checkout>/frontend
   git ls-files -z | rsync -a --from0 --files-from=- ./ <scratch>/frontend/
   cd <scratch>/frontend
   pnpm install --frozen-lockfile --ignore-scripts
   ```

3. Lint once with the current release as the baseline. The frontend's `pnpm lint` forwards its
   arguments to ESLint:

   ```sh
   pnpm lint --format json --output-file <scratch>/base.json
   ```

4. Point the catalog entry for `@rotki/eslint-config` in `pnpm-workspace.yaml` at
   `file:<scratch>/pack/rotki-eslint-config-<version>.tgz`, run
   `pnpm install --no-frozen-lockfile --ignore-scripts`, and lint again into `new.json`.
5. Compare the two reports by file, line and rule. Only the differences matter: the baseline can
   already contain errors on the frontend's current branch.

For a single rule, a quicker check is a minimal flat config that loads only that plugin (from this
repository's `node_modules`) and the TypeScript and Vue parsers, run with `--no-config-lookup` over
the same copy.

## Upstream sync

The repository follows antfu/eslint-config selectively. `.upstream-sync` holds the upstream version
last reviewed.

1. List upstream changes since then:

   ```sh
   gh api repos/antfu/eslint-config/compare/<last>...main
   ```

   Read the release notes of any major. Much of a large upstream diff can be upstream reformatting
   its own source, so diff the `src/configs/` hunks for actual rule and option changes.

2. For each change, check whether rotki already has an equivalent, and whether it suits rotki.
   Measure anything that changes lint results against the frontend.
3. Port what fits in its own commit (`feat: sync ...` or a focused `feat(<area>): ...`), and list
   what was skipped and why in the commit body (see `6716864` and `2127022`).
4. Move `.upstream-sync` forward only when everything up to that version has been decided.
   Something deferred keeps the marker at the version before it.

## Dependency updates

Renovate lists updates on the Dependency Dashboard issue and opens pull requests only on approval
(`.github/renovate.json5`). The dashboard can lag behind npm, so check npm directly.

**Prefer one batched update over approving Renovate pull requests one at a time.** Use the
dashboard as the checklist, and do a maintenance pass by hand when updates have piled up (roughly
monthly) and before a release. A batch is a single branch and pull request with a few commits, so
the lockfile is resolved once, CI, review and the frontend check run once, and interactions between
updates show up together: two plugins fixing the same code, a preset whose defaults changed, a
transitive package that two updates share. Renovate notices the merged versions and clears those
dashboard entries by itself.

Tick a single dashboard box only for an update that cannot wait for the next batch, such as a fix
for a security advisory or a bug that blocks the frontend. The procedure below is the batched
pass.

### Policy

- **7-day release-age cooldown** in both `.github/renovate.json5` and `pnpm-workspace.yaml`.
  `@rotki/eslint-plugin` is excluded so a companion fix can be picked up the same day.
- **Node types follow the supported runtime.** Renovate restricts `@types/node` and `node` to 24.x,
  and pnpm to 12.x. Update those limits when the runtime or package manager moves.
- **TypeScript is capped by typescript-eslint.** Check
  `npm view @typescript-eslint/typescript-estree@<version> peerDependencies` before a TypeScript
  major.
- Runtime dependencies are pinned exactly (`saveExact: true`), so consumers get exactly what was
  tested. Add them with `pnpm add -E`.
- GitHub Actions are pinned by commit SHA with the version in a trailing comment.

### Procedure

1. Start from an up to date `main` on a branch such as `chore/deps-update`.
2. Gather the state: `pnpm audit`, `pnpm outdated`, and the dashboard
   (`gh issue list -R rotki/eslint-config --search "Dependency Dashboard in:title"`).
3. Check publish dates (`npm view <package> "time[<version>]"`) and skip anything younger than 7
   days.
4. Bump minor and patch versions first, keeping monorepo packages in lockstep (all
   `@typescript-eslint/*`, both `@commitlint/*`). Update pnpm with `corepack use pnpm@<version>`
   and action pins with `gh api repos/<owner>/<repo>/commits/<tag> -q .sha`.
5. Refresh vulnerable transitive packages with `pnpm update --depth Infinity <package> ...` and
   check that `package.json` gained no direct dependencies. Optional peers (storybook, vue-i18n)
   are installed into this repository's lockfile too; refreshing them clears advisories that only
   exist here. Trace what remains with `pnpm why` and fix it upstream rather than with overrides.
   An `overrides` entry here does not reach consumers anyway.
6. Rebuild, run the tests, and read the snapshot changes.
7. Handle majors separately: read each changelog, check how the configs use the plugin (several
   spread an upstream preset such as `configs.customize()` or `configs.recommended`, so changed
   defaults arrive silently), apply, and compare snapshots and fixtures with the minor-only state.
   Measure the result against the frontend. Watch for rule overlaps (two rules fixing the same
   node) and for deprecation warnings, which every consumer would see on each run.
8. Commit in parts: `ci: update github actions`, `chore(deps): update dependencies`, and one commit
   per major or group of majors that explains any config adaptation and its effect on consumers.

## Workflow changes

Changes under `.github/workflows/`, including pin bumps, must pass two tools that cover different
things:

- [actionlint](https://github.com/rhysd/actionlint) checks that workflows are valid: YAML and
  workflow syntax, expression types, `needs` and matrix references, action inputs, and the shell
  scripts in `run:` steps (through shellcheck).
- [zizmor](https://docs.zizmor.sh/) checks workflow security: permissions, credential persistence,
  template injection and pins. Its online audits also catch impostor commits, pins whose SHA does
  not match the version comment and actions with known vulnerabilities.

The `workflow-lint` job in `ci.yml` runs both on every push and on pull requests that change
`.github/`. Run the same versions locally before committing (needs Docker and `uv`; the token
enables zizmor's online audits):

```sh
GH_TOKEN=$(gh auth token) pnpm run lint:workflows
```

The actionlint image digest and the zizmor version are pinned in both `ci.yml` and the
`lint:workflows` script. Move them together, and keep them in step with `rotki/eslint-plugin` and
`rotki/ui-library`.

The baseline is no findings. Fix new findings rather than suppressing them. If one has to stay,
suppress that single line with a `# zizmor: ignore[<audit>] <reason>` comment, never without a
reason. Keep the existing patterns: `permissions: {}` at the top level
with per-job grants, `persist-credentials: false` on checkout, SHA pins with a version comment, and
expressions that carry outside input passed to `run:` through `env:`.

## Releasing

Releases are tag driven. Pushing a `v*` tag runs `.github/workflows/release.yml`.

1. Make sure `main` is green and contains everything for the release.
2. Pick the version (see Versioning) and run `pnpm run release` (`bumpp -r --no-push`). It bumps
   `package.json`, commits `chore: release vX.Y.Z` and tags it locally.
3. Push the commit and tag to `rotki/eslint-config`:

   ```sh
   git push <rotki-remote> main --follow-tags
   ```

4. The workflow creates the GitHub release with `changelogithub`, then the `publish` job waits for
   approval in the `npm` environment. After approval it publishes with provenance through npm
   trusted publishing. `pnpm publish` builds through the `prepack` script.
5. Verify with `npm view @rotki/eslint-config version` and
   `gh release view vX.Y.Z -R rotki/eslint-config`. The registry can take a few minutes to serve a
   new version.
6. Update the frontend's catalog entry, and apply any auto-fixes the release needs there in the
   same change.

### Versioning

What counts is the effect on consumers' lint results:

- **Patch:** fixes, fewer false positives, dependency updates that change no results.
- **Minor:** new opt-in configs or options, new rules that report nothing on the frontend, and small
  auto-fixable changes that the frontend update fixes in a handful of files.
- **Major (`feat!`):** rules that report new errors by default beyond that, removed or renamed
  options or configs, raised peer or Node requirements. Previous majors include enabling stricter
  TS and Vue rules and banning `else` after returns.

## Repository settings

These live in GitHub and npm, not in the repository. Keep this list current when they change.

- `main` is protected: 1 approving review with code owner review required, and the
  `license/cla`, `Commit Lint`, `Workflow lint` and `Build & Test` checks must pass.
- `CODEOWNERS` assigns everything to `@rotki/maintainers`, which has write access.
- The `npm` environment allows only `v*` tags and requires a reviewer to approve each publish.
- npm package owners are managed on npmjs.com.
